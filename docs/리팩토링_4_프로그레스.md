  - **지시서 ↔ 코드 불일치 ①(발견 대상 상태)**: 지시서 2.1은 대상을 `match_status='unmatched'`로 한정했지만, 3.4는 "다인용 PDF의 모호 페이지가 발견 스테이지에 자연 편입된다"고 적었다. 실제 코드(`ingest/actions.ts`의 `ingestMultiPagePdf`)는 모호 페이지를 **`pending_confirm` + raw NULL**로 넣으므로 'unmatched'만 보면 편입되지 않는다. 게다가 지시서 2.3의 `listDiscoveredStudents`는 이미 `IN ('unmatched','pending_confirm')`이다. 두 지시가 모순이라 **3.4의 명시된 목표를 만족하는 쪽**으로 통일해 `DISCOVERY_STATUSES = ['unmatched','pending_confirm']` 상수를 세 액션이 공유하게 했다. 발견은 raw만 채우므로 pending 행을 대상에 넣어도 큐 상태·귀속에 영향이 없다(정보만 추가).
  - **지시서 ↔ 설계 판단 ②(집계 제외 규칙 확장)**: 지시서는 "명단과 **모호하지 않게** 일치하는 그룹 제외"였으나, 구현은 **명단에 학번이 있거나 이름이 있으면(동명이인 포함) 제외**하는 더 넓은 규칙을 썼다. 이유: 검토 표는 기본 전체 선택이라, 동명이인 후보가 섞여 있으면 교사가 그대로 승인해 **같은 이름의 중복 학생**이 생긴다. 발견의 목적은 *신규* 학생 발굴이고, 명단에 이미 있는 이름의 귀속은 확인 대기 큐(`attributeExisting`/`attributeNew`)가 담당한다 — CLAUDE.md 보수 원칙("애매하면 자동 처리하지 않고 교사 확인 큐로")에 맞춘 선택. 테스트로 고정했다.
  - **`applyClassification` 재사용 안 함**: 지시서 2.4는 재사용을 허용했으나, 이 헬퍼는 `classifyMatch`를 타서 **column 출처 신규 학번이면 학생을 자동 생성**한다. 교사 승인 게이트를 세우는 액션 내부에서 그 경로가 도는 것은 취지에 어긋나므로, 재귀속은 "학번 완전 일치 또는 이름 유일 일치"만 반영하는 별도 결정적 루프로 구현했다. **기존 호출부·시그니처는 무변경**.
  - **`finalizeDiscovery` 신설(공유 계약에 없던 이름)**: `RunPlan`은 `finalize`가 필수 필드라 스테이지마다 하나가 필요하다. 기존 `finalizeIngest`·`finalizeMatching` 관행을 그대로 따랐다(revalidate만).
  - **LLM 실패 처리**: 429/503/529는 `retryable: true` 실패로 반환해 풀의 백오프 재시도에 맡기고, 그 외 오류는 **파일명 폴백**으로 살린 뒤 메시지에 실패 사유를 덧붙인다(지시서의 "LLM 실패 시 파일명 폴백"과 "429 retryable"을 둘 다 만족시키는 절충). 식별 실패는 오류가 아니므로 `ok: true`(매칭 관행과 동일 — 서킷 브레이커 오발 방지).
  - **eslint 신규 규칙 대응**: 처음 작성한 검토 패널이 `react-hooks/set-state-in-effect`·`react-hooks/refs`에 걸렸다(effect 본문에서 동기 setState / 렌더 중 ref 쓰기). 조회 경로를 effect 하나로 단일화하고(`reloadNonce` 트리거 + cancelled 가드) 기존 `book-select-modal.tsx`의 프라미스 체인 관용구를 따라 해소했다. `onCountChange`는 effect 의존성이므로 **참조가 안정된 함수**여야 한다는 주석을 prop에 달았다(현재 소비자는 useState setter).
  - **다인용 PDF 경로 무변경 확인**: `ingestMultiPagePdf`는 로직을 건드리지 않았다. 모호 페이지는 위 ①에 따라 발견 대상에 포함된다.
  - **다음 배치(3) 인계**: 작업결과표는 여전히 `student_id NOT NULL`만 조회하므로(대시보드 `page.tsx`의 wsSubs), 발견·승인 전 제출물은 표에 보이지 않는다 — 배치 3의 미귀속 배너(`unassignedCount`)가 이 구멍을 메운다. 미귀속 카운트를 셀 때 발견 스테이지가 raw를 채워도 `match_status`는 그대로라는 점(unmatched/pending_confirm 유지)을 전제로 하면 된다. `components/projects/dashboard/discovery-review.tsx`는 배치 3의 [학생 이동] UI와 겹치지 않는다(검토=신규 학생 생성, 이동=기존 학생 재귀속).

#### 사용자 확인 필요 (에이전트 미수행 — OAuth·실 LLM 과금 필요)

1. **명단 빈 프로젝트 부트스트랩**: 학생 A만 있는 파일 + B만 있는 파일 + C 섞인 파일을 업로드 → [수합 & 매칭] → 터미널에 **수합 → "── 다음 단계 ──" → 발견 → "── 다음 단계 ──" → 매칭** 3연쇄가 흐르는지.
2. **발견 로그**: 건별로 `→ 학번 10203·이름 홍길동 (LLM)` / `(파일명)` / `→ 식별 실패`가 찍히는지. 문서에 없는 값을 LLM이 지어내면 저장되지 않아야 한다(실존 대조).
3. **검토·승인**: 실행 종료 후 "학생 명단 검토 (N)" 표에 A·B·C 합집합이 뜨고, [선택 학생을 명단에 추가하고 재매칭] 한 번으로 "학생 N명 추가 · 제출물 M건 귀속" 피드백 + 작업결과표에 행이 생기는지.
4. **이름 충돌**: 같은 학번에 다른 이름이 섞인 경우 라디오로 이름을 고를 수 있는지.
5. **중단·증분**: 발견 스테이지 진행 중 일시정지·재개·긴급 중단이 동작하고, 재실행 시 이미 식별값이 있는 건은 `→ 이미 식별값 있음`으로 건너뛰는지.
6. **자동 생성 불확대**: 검토 표에서 아무도 선택하지 않으면 학생이 **하나도** 생기지 않는지(스프레드시트 열 학번의 기존 자동 생성만 유지).
