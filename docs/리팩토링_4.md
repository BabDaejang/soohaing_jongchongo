## [공통 프롬프트] — 모든 배치 대화의 서두에 포함

너는 수행평가 수합·평가·생기부 생성 웹앱(**soohaing_jongchongo** — Next.js App Router + TypeScript strict + Tailwind + Supabase, 배포 Vercel) 저장소에서 `docs/리팩토링_4.md`의 **배치 하나만** 실행하는 개발자다.

### 시작 절차 (반드시 순서대로)

1. CLAUDE.md 세션 프로토콜대로 `docs/SPEC.md` → `docs/DATA_MODEL.md` → `docs/PROGRESS.md` → `docs/DECISIONS.md`를 읽는다.
2. `docs/리팩토링_4_프로그레스.md`를 읽고(없으면 배치 1이 신설) 앞 배치 완료 여부와 워킹 트리 청결(`git status`)을 확인한다. 어긋나면 멈추고 사용자에게 보고한다.
3. 이 문서의 [문제 진단]·[배경]·[공유 계약]·[불변 규칙]과 지시받은 배치 절만 정독한다. **다른 배치의 작업은 하지 않는다.**
4. 수정할 파일은 **수정 전에 반드시 전체를 읽는다.** 이 문서와 실제 코드가 어긋나면 **코드가 기준** — 확인 후 프로그레스 문서에 특이사항으로 기록한다. 특히 `app/projects/[id]/submissions/actions.ts`·`app/projects/[id]/ingest/actions.ts`·`app/projects/[id]/evaluate/actions.ts`·`app/projects/[id]/records/actions.ts`·`components/projects/worksheet/worksheet-table.tsx`·`components/projects/dashboard/phase1-panel.tsx`·`lib/hooks/use-sequential-run.ts`는 이 지시서가 2026-08-20 시점 코드 기반으로 서술한 것이므로 실제 시그니처·구조를 재확인하고 어긋나면 코드에 맞춘다.

### 배경 (사용자 결정 P-1~P-9, 2026-08-20 — 이 문서의 사용자 승인으로 확정, 각 배치 실행 시 DECISIONS에 기록)

- **P-1 (로스터 부트스트랩, 승인 경유)**: 수합의 목적은 "업로드된 모든 파일에서 학생을 찾아 **합집합 명단**을 만들고 학생별로 제출물을 모으는 것"이다. 이를 위해 수합 실행에 **발견(discovery) 스테이지**를 추가한다 — 명단 없이도 파일 내용·파일명에서 식별값(학번·이름)을 추출해 `raw_student_no/name`에 저장하고, 발견된 신규 학생을 집계해 **교사 일괄 검토·승인 화면**에서 명단에 추가한다. 자동 생성 원칙은 불변: `classifyMatch`의 자동 신규 생성은 여전히 column 출처 학번뿐이고, 발견분은 **교사 승인을 경유해서만** 학생이 된다(유령 학생 방지 — CLAUDE.md 보수 원칙). LLM 추출 식별값은 **문서 앞부분에 토큰이 실존할 때만** 저장한다(스니펫 실존 대조 — 팩트시트 `filterBySnippetMatch`와 같은 구조적 할루시네이션 차단).
- **P-2 (수정 허브 = 작업결과표)**: 매칭·평가·생기부의 확인과 수정은 작업결과표를 허브로 모은다. 미귀속 제출물(unmatched·pending_confirm)은 지금 표에 전혀 안 보이는데, **배너로 노출**하고 제출물 펼침에 매칭 배지·[학생 이동]을 단다. 모든 수정 액션은 성공 피드백과 작업결과표 갱신(`emitWorksheetRefresh`)을 동반한다.
- **P-3 (평가 교사 수정)**: 기준별 채점 결과를 작업결과표 제출물 펼침에 표시하고, 교사가 기준별 점수를 직접 수정할 수 있게 한다. 수정은 evaluations에 **`origin='teacher'` 새 행 insert**(records의 'edited' 버전 패턴과 동일 — 이력 보존, LLM 원본 불변)로 구현하고, 쓰기는 기존 관행대로 **서버 액션 내 service role**(requireProjectOwner + 감사 로그 경유)로 한다. RLS 정책은 바꾸지 않는다(클라이언트 직접 쓰기 여전히 불가 — 위조 차단 유지). 수정 직후 `recomputeAndSave`를 호출해 점수→순위→등급이 즉시 재파생된다.
- **P-4 (등급은 파생 불변, 목표 등급 헬퍼)**: 등급 직접 수정은 INV-6 위반이라 **도입하지 않는다**. 대신 반영 점수 보정 편집기에 "목표 등급" 선택을 추가해, 그 등급이 되는 보정 점수 범위를 순수 함수로 계산해 자동 입력해 준다(등급은 여전히 점수에서 파생 — INV-6 보존). 인원·비율상 불가능한 등급은 "현재 인원 기준 불가"로 표시한다.
- **P-5 (평가 = 선택 단계)**: 페이즈 2는 "선택"임을 UI에 명시한다. 생기부 생성은 평가 없이 동작함을 문구로 보증한다(코드상 이미 독립 — 회귀 방지 확인만).
- **P-6 (팩트시트 독립 + 전역 내비게이션)**: 전역 헤더 내비게이션(프로젝트·팩트시트·계정·관리자)을 도입해 `/factsheets`를 1급 목적지로 만든다. 페이즈 2의 진실성 검증 연계(대조·자동 생성)는 불변 — 바뀌는 것은 관리 동선뿐이다.
- **P-7 (브리프 = 프롬프트 프로필 확장)**: 활동 맥락·강조 포인트는 프로젝트별 **작성 브리프(markdown 자유 서술)**로 담고, 기존 `prompt_profiles`(+`prompt_profile_versions`)에 `brief_md` 컬럼을 추가해 기존 버전·이력·MD 입출력 기계를 그대로 탄다(새 테이블·새 편집 체계 금지). 병합 규칙: 프로젝트 오버라이드의 brief가 비어 있지 않으면 그것만, 비어 있으면 계정 기본의 brief. 브리프는 생성 프롬프트에 별도 섹션으로 주입되고, "최종 프롬프트 미리보기"로 교사가 실제 주입 내용을 확인할 수 있다.
- **P-8 (브리프 AI 협업, 자동 반영 금지)**: AI 초안 생성(활동 설명·강조 포인트 폼 + 자유 서술 + 평가계획서류 파일 텍스트) 및 다듬기(현재 브리프 + 수정 요청)를 제공하되, **AI 출력은 저장하지 않고 편집기에 채워만 준다**. 저장은 항상 교사의 명시적 저장(새 버전)이다 — 예시 인제스트(`analyzeExample`/`applyProfileSuggestions`)와 동일한 무자동반영 원칙.
- **P-9 (의존성·스타일)**: 새 npm 의존성 추가 금지. 마크다운 편집기는 textarea 기반(렌더러 도입 금지 — 브리프의 소비자는 LLM이다). 기존 화면의 스타일 관용구(neo-brutalism 대시보드 / zinc 계열 작업결과표)를 해당 화면의 기존 코드에 맞춘다.

### AI 개입 지점과 할루시네이션 가드 원칙 (사용자 질문 4에 대한 설계 답)

원칙: **AI 출력이 곧바로 사실·데이터가 되는 경로를 만들지 않는다.** 모든 AI 출력은 ①결정적 대조(명단 경계·토큰 실존·스니펫 실존), ②교사 승인 큐, ③검증 패스 중 최소 하나를 거친다. 이 원칙 아래 단계별 현황과 이번 확장:

| 단계 | 기존 AI | 이번 리팩토링 추가 | 가드 |
| --- | --- | --- | --- |
| 수합 | 열 매핑 추천·비전 OCR | — | 교사가 매핑 확정 / OCR은 원문 전사 한정 |
| 매칭 | 명단 내 1명 지목(명단 밖 응답 폐기) | **발견: 명단 없이 식별값 추출(배치 2)** | 추출 토큰의 문서 내 실존 검증 + 교사 일괄 승인 경유(자동 학생 생성 없음) |
| 평가 | 루브릭 제안(승인만 반영)·채점(근거 인용 필수)·진실성 검증(플래그만) | 기준별 결과 노출 + **교사 수정(origin='teacher')** | 수정은 이력 보존 insert + 감사 로그, 등급은 파생 불변 |
| 팩트시트 | 수집 원문 추출·정제 | — | 스니펫 실존 대조(`filterBySnippetMatch`) 불변 |

## [배치 2 프롬프트] — 수합 학생 발견(로스터 부트스트랩)

`docs/리팩토링_4.md` 배치 2를 실행하라. 전제: 배치 1 완료. 범위: 발견 스테이지(순수 함수 + 서버 액션 + 실행 체인 편입) + 학생 명단 검토·일괄 승인 UI + 승인 시 결정적 재귀속. **마이그레이션 없음** — 식별값은 기존 `submissions.raw_student_no/raw_student_name/identity_source`를 재사용한다(0011의 'llm'·'filename' 값 그대로).

### 설계 — 실행 흐름 (이 배치 완료 시점의 목표)

```text
[수합 & 매칭] = 스테이지 연쇄 (useSequentialRun)
  S1 수합   : 기존 prepareIngest / ingestOneFile / finalizeIngest 그대로
  S2 발견   : 미매칭·식별값 없는 비스프레드시트 제출물 1건 단위 —
              LLM이 명단 없이 문서 앞부분에서 {학번, 이름}을 추출 →
              추출 토큰이 본문에 실존할 때만 raw_* + identity_source='llm' 저장.
              LLM 실패·무식별이면 파일명 후보(extractIdentityCandidatesFromFilename)로 폴백
              → raw_* + identity_source='filename' 저장. 매칭·학생 생성은 하지 않는다.
  S3 매칭   : 기존 prepareMatching / matchOneByLlm / finalizeMatching 그대로
              (S2가 raw를 채워 두므로 결정적 분류가 대부분을 처리하고,
               명단에 없는 식별값은 pending_confirm 큐 + 발견 검토 대상이 된다)

[학생 명단 검토] (실행 종료 후 Phase1Panel 상시 섹션)
  listDiscoveredStudents가 미귀속 제출물의 raw 식별값을 집계(명단 제외, 학번 우선 그룹핑)
  → 교사가 체크박스로 선택·이름 충돌 해소 → [선택 학생을 명단에 추가하고 재매칭]
  → createDiscoveredStudents: students insert + 해당 식별값의 미귀속 제출물 결정적 재귀속
```

### 1단계 — 순수 함수 (`lib/matching.ts` 확장)

1. `extractIdentityCandidatesFromFilename(filename: string | null): { no: string | null; nameCandidates: string[] }`
   — `fileBasename` 재사용. 학번 후보: 4~6자리 숫자 토큰(`containsToken` 경계 규칙과 동일한 앞뒤 숫자 비접속)이 **정확히 1개**일 때만 채택, 아니면 null. 이름 후보: 한글 2~4자 토큰 전부(검토 UI에서 교사가 거르므로 과보수 불필요 — 단 "최종"·"수행"·"평가"·"제출"·"과제" 등 명백한 상용어 최소 스톱워드는 상수로 제외).
2. `aggregateDiscoveredIdentities(rows: { no: string | null; name: string | null; source: IdentitySource | null; submissionId: string }[], roster: StudentRef[]): DiscoveredStudent[]`
   — 그룹 키: 학번(trim) 우선, 학번 없으면 이름. 명단과 **모호하지 않게 일치**(학번 완전 일치 또는 이름 유일 일치 — classifyMatch와 동일 기준)하는 그룹은 제외(매칭 재실행이 처리할 몫). 반환 항목: `{ no, name, submissionIds, sources, conflict }` — 같은 학번에 서로 다른 이름이 모이면 `conflict: string[]`(이름 목록)로 표시. 순수 함수 — 단위 테스트 대상.
3. 기존 `classifyMatch`·`deriveIdentityFromFilename`은 **수정하지 않는다**.

### 2단계 — 발견 서버 액션 (`app/projects/[id]/submissions/actions.ts`)

1. `prepareDiscovery(projectId)` → `{ targets, prelude }`: 대상 = `match_status='unmatched'` AND `raw_student_no IS NULL AND raw_student_name IS NULL` AND source_type NOT IN ('xlsx','csv'). prelude에 대상 수. (스프레드시트 행은 column 값이 이미 있고, 다인용 PDF 분할분 등 raw가 비어 있는 것이 대상이다.)
2. `discoverOne(projectId, submissionId)` → `{ ok, message, retryable? }`:
   - content_text 앞 1500자를 명단 **없이** 읽어 `{"student_no": string|null, "name": string|null}`만 추출하는 프롬프트(callLLM purpose='매칭', temperature 0, maxTokens 200). 근거를 작성자 식별 정보(이름란·학번란·머리말·서명)에 한정하고 불확실하면 null을 지시한다 — `extractIdentityByLLM`의 기존 문구 관행 재사용.
   - **실존 검증(구조적 환각 차단)**: 추출된 no·name 각각 `containsToken(head1500, 값)`이 참일 때만 인정. 둘 다 탈락하면 파일명 폴백: `extractIdentityCandidatesFromFilename` 결과에서 no 또는 nameCandidates가 **정확히 1개**일 때만 채택(2개 이상이면 후보 확정 불가 → 저장 없이 "식별 실패" 메시지).
   - 인정된 식별값을 `raw_student_no/raw_student_name` + `identity_source`('llm' 또는 'filename')로 update. **student_id·match_status는 건드리지 않는다.**

### 3단계 — 목표 등급 헬퍼 (`lib/grading.ts` 추가)

`overrideRangeForGrade(otherScores: number[], scheme: GradingScheme, tieBreak: TieBreak, targetGrade: number): { min: number; max: number } | null`
— otherScores는 대상 학생을 **제외한** 나머지 학생들의 effective 점수. 후보 점수 0~999에 대해 `computeStandings([...otherScores, 후보], …)`로 대상 학생의 등급을 판정, 목표 등급이 되는 정수 구간을 이진 탐색(등급은 점수에 단조)으로 구한다. 불가능하면 null. `computeStandings`·`GRADE_BOUNDARIES`는 호출만 하고 수정 금지. **신규 테스트 ≥ 8건**(5/9등급, 경계, 동점 tie_break 양쪽, 소인원 불가 케이스, 전 구간 단조성 스팟 체크).
